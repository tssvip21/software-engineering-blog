# [개선 13] 읽기 쉬운 숫자와 끝까지 이어지는 완료 동작

> 2026-11-16 로컬 초안. 사용자 검토 전이며 게시하지 않았다.

## 같은 숫자라도 어떻게 보여 주는지가 달랐다

9차에서는 숫자가 틀렸다는 문제와 읽기 어렵다는 문제를 나눴다. 치약 잔량 0.055kg은 계산상 맞지만, 물품을 확인하는 사람에게는 55g이 더 바로 읽힌다. 1.234분처럼 세 자리 소수로 보여 주던 시간도 1분 14초처럼 표현했다. 반면 몸무게는 현재 표시를 유지하라는 사용자의 선택을 따랐다.

모든 숫자를 소수 첫째 자리로 자르는 방법은 쓰지 않았다. 그렇게 하면 작은 소비량이나 변화가 0이 되고, 실제 약 용량도 달라 보일 수 있다. 표시와 원값을 분리하고 단위·비교 문맥에 따라 자릿수를 정했다. 작은 비영 값, 실제 0, 미입력, 계산할 수 없음은 서로 다르게 남겼다. 포장 개수를 모르면 만들어 표시하지 않았다.

## 가독성을 한 화면의 글자 크기로 끝내지 않았다

오늘과 기능 보드뿐 아니라 전체 기록·원기록 상세·표·그래프·루틴·물품·설정·입력창을 같이 확인했다. 글자 크기를 바꿔도 이전 스타일이 덮어쓰는 부분이 있었고, 숫자와 붙은 단위나 보조 링크가 여전히 작게 남는 경우도 있었다. 같은 자료와 화면 폭의 전후 화면을 비교하고, 글자 크기·대비와 버튼 위치를 함께 조정했다.

빠른 기록은 제목 옆에 현재값을 두고 설정값과 실행 버튼을 아래에 모았다. 빈 공간을 설명 문장이나 배지로 채우지 않았다. 카드가 짧아져도 같은 행의 주요 버튼은 하단에 맞추고, 좁은 화면에서는 내용에 따라 줄이 바뀌도록 했다.

## 루틴을 체크했는데 무엇이 빠졌는지 모르는 문제

기존에는 상세 기록에 필요한 값이 없으면 완료되지 않고 일반적인 필수 오류만 나왔다. 모든 루틴에 강제로 기본값을 넣는 대신, 현재 검증을 그대로 통과하는 항목은 바로 완료하고 필요한 항목이 있으면 그 자리에서 입력하도록 나눴다.

입력창의 날짜·시각을 브라우저가 비워 버리는 실제 오류도 발견했다. 시간대가 붙은 문자열을 입력값에 직접 넣었던 부분을 고쳐 기존 Django 위젯이 표시용 값으로 변환하게 했다. 취소하거나 검증에 실패하면 루틴은 미완료로 남고, 같은 요청이 다시 오면 같은 결과를 확인한다.

마지막에는 요청 번호뿐 아니라 요청 대상도 검사했다. 다른 루틴 주소로 같은 본문을 보내거나 역할 변경 후 이전 결과를 다시 요청하는 두 경우를 재현했고, 루틴·날짜·조회 권한을 함께 확인하도록 보완했다. 수정 전 실패와 수정 후 통과를 남겼다.

## 같은 코드가 다른 저장소에서도 실행되는지

SQLite에서는 통과했지만 실제 PostgreSQL 조회에서 트랜잭션 밖 행 잠금 오류가 나타났다. 읽기 권한을 갱신하는 경로를 올바른 트랜잭션으로 묶고, 테스트가 자동으로 트랜잭션을 제공해 이 문제를 숨기지 않도록 별도 검사를 추가했다.

초기 9차 판본에서는 SQLite·PostgreSQL 자동 검사 각각 467개와 Chromium·Firefox 30개 흐름·90개 화면 조건을 확인했다. 아래 후속 보완을 포함한 최신 자동 검사는 두 DB에서 각각 484개 통과했다. 설치된 Windows Chrome·Edge에서도 복사 DB의 저장·수정·재조회와 모바일 루틴을 시험했다. 수치는 실행한 검사의 범위이며 실제 보호자 장기간 사용성 실험을 뜻하지 않는다.

## 기존 서비스에 반영하면서 지킨 경계

9차 지시서는 기존 클라우드 재배포를 승인했지만 GitHub 업로드는 검수 뒤로 남겼다. 두 권한을 섞지 않았다. 기존 VM을 다시 켠 뒤 달라진 IP에 맞춰 주소와 Google 인증 경로를 확인하고, 환경·소스·DB를 백업한 뒤 검증된 이미지를 적용했다. 소스는 로컬 커밋에서 선별한 파일로 묶었고 환경 파일·개인 자료·DB를 배포 패키지에 넣지 않았다.

실제 계정으로 로그인할 수 있는 것과 운영에서 새 돌봄 기록을 작성하는 검사는 구분했다. 로그인과 기본 화면 접근은 확인했지만, 실제 입력 자료나 검증 자료 생성 승인 없이 운영에 가상 돌봄을 남기지는 않았다. 후속 native 브라우저 연속 검사에서는 안전하게 작업 창을 제어하지 못해 전체 통과로 세지 않았다.

Mac도 Windows 검사 결과로 대체하지 않았다. 실행 명령과 이미지의 아키텍처 호환을 확인했지만 실제 Mac 연결을 확보하지 못했다. 이 부분과 운영 기록의 저장·수정 검증은 남아 있다. 무료 크레딧 잔액도 확인하지 못했으므로 무료라고 단정하지 않았다.

현재 운영 소스는 후속 보완을 포함한 `0ce40737e363`, 주소는 https://taily-35-254-83-9.sslip.io 이다. [수치 기준과 검증 범위](../../docs/26_테일리_9차_가독성과수치표현.md)에 실제 확인한 것과 미완료 항목을 분리했다. 전후 캡처는 PC의 `tmp/handoff/phase9/before/`, `after/`에 보관한다.

## 후속 검수: 물품의 개수와 내용물은 다른 정보다

검수에서 치약의 kg를 g으로 바꾼 것만으로 물품 수량의 사용 맥락을 충분히 개선한 것은 아니라는 점을 확인했다. 물품마다 포장 이름과 용량을 등록하고, 입고는 포장 수로 적되 남은 내용물은 무게·부피로 읽을 수 있게 보완했다. 치약 같은 용기는 개수와 포장 기준 용량을, 사료는 봉지당 용량과 실제 남은 양을 구분한다. 50개들이 패드의 팩 수와 패드 낱개 수도 섞지 않는다.

과거 입고량이 현재 포장 용량으로 다시 계산되지 않도록 당시 정보를 기록에 보관했다. 검사 중 포장 정보 수정 직후 같은 요청을 다시 보내면 제품 설명의 판본 때문에 다른 요청으로 판단되는 문제를 발견해, 당시 물품 정보도 함께 유지하도록 수정했다. 정상 재시도는 한 번만 저장하고 내용이 달라진 재요청은 거부한다. 추가 검사까지 SQLite·PostgreSQL 각각 484개가 통과했다.

루틴 입력창을 연 뒤 기능이 비활성화되는 경우와 미래 날짜 접근에서 서버 오류가 나던 경계도 고쳤다. 작성한 내용과 이유를 보여주며 완료로 처리하지 않는다. 빠진 Docker 실행 파일은 이번 로컬 커밋에 포함한다. GitHub 업로드는 사용자 검수 뒤에 진행한다.

사용자가 생활에서 쓰는 것처럼 예시를 채워 달라고 요청해 기존 시연 물품 13개에 포장 정보를 넣고, 예비 샴푸 한 병과 입고·사용 기록 6개를 추가했다. 사료는 봉지 용량과 남은 내용물, 패드·바닥 종이는 묶음과 낱개, 예비 샴푸는 병 수와 개당 용량으로 비교할 수 있다. 추가한 용량·구매·사용 상황은 가상 생활 설정이다. 공간 이름도 사용자 요청대로 강아지·고양이·앵무새로 바꿨다. 원래 기록을 보존하며 로컬 시연 DB만 수정했고 운영 데이터에는 넣지 않았다.
