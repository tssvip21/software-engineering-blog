# 테일리 3차 수정 계획

2차 개선 화면을 사용하며 모은 13개 피드백이다. 아래 본문과 항목별 상태 문구는 실행 전 논의 기록으로 보존한다.

**2026-11-05: 13개 항목의 로컬 구현과 자체 검증을 완료했다.** 실제 반영 내용·검사 범위·남은 확인은 [3차 개선 결과](13_테일리_3차개선.md)를 따른다. GitHub 업로드나 외부 배포 완료를 뜻하지 않는다.

## 의존관계에 따른 권장 작업 순서

아래는 재작업을 줄이기 위한 권장 순서다. 실제 구현 담당자가 현재 코드와 데이터의 의존관계를 확인한 뒤 유지·변경하거나 독립 작업을 병행할 수 있다. 순서를 바꾸기 위해 사소한 결정을 매번 사용자에게 묻지 않는다. 실행 순서에 대한 재량과 사용자가 정한 요구사항을 변경하는 것은 구분한다.

‘모듈·UI·로직’은 논의를 위한 큰 범주이며 고정된 작업 경계가 아니다. 구현 담당자는 의존관계와 변경 목적에 따라 작업을 더 세분화하거나 연관된 부분을 함께 처리할 수 있다. 커밋도 이 큰 범주에 억지로 맞추지 않고, 무엇을 왜 바꿨는지 설명되는 실제 변경 단위로 나눈다. 작업하면서 이력을 남기며, 완료 후 과정을 꾸며 쪼개지 않는다. 로컬 커밋과 GitHub push는 별개이며, push·PR 생성·외부 배포는 이번 실행 범위에 포함하지 않는다.

1. **현재 구조와 변경 영향 확인:** 관련 저장 구조, 모듈 식별자·설정, 권한 처리, 기록·통계와 화면 사이의 연결을 필요한 범위에서 파악한다. 기존 검사·조사 결과를 활용하고 변경 판단에 필요한 부분을 확인한다.
2. **분석 방법과 UI·UX 조사:** 종합 상태를 산출할 이론·수학적 방법과 다수 정보를 다루는 화면 구성 방식을 조사한다. 이 단계에서는 화면의 최종 배치나 특정 계산법을 먼저 고정하지 않는다.
3. **공통 구조와 입출력 설계:** 기본 모듈 분류, 사용자 그룹, 분석 영역의 관계를 함께 설계한다. 분석에 필요한 기록·단위·기간과 결과·근거·자료 부족 상태를 정의하고, 화면과 공유할 데이터 구조 및 권한 범위를 정한다.
4. **공통 기반과 분석 로직 구현·검증:** 필요한 저장·그룹 관리·권한 연결을 먼저 마련하고, 이를 사용하는 종합 상태 로직과 보조 비교를 구현한다. 서로 다른 기록 조합에서 결과가 어떻게 달라지는지 확인해 계산의 의미와 출력 구조를 정리한다. 기존 데이터 보존도 이 단계에서 확인한다.
5. **실제 결과에 맞춘 UI·UX 설계:** 확인된 분류·그룹과 분석 결과를 바탕으로 돌봄 모듈, 전체 기록, 통합 상태의 배치와 이동 흐름을 설계한다. 빈 공간·정보량·스크롤과 화면별 역할을 함께 조정한다.
6. **공통 UI와 개별 화면 구현:** 영향을 공유하는 컴포넌트와 조작부터 정리하고 개별 화면에 적용한다. 분류·사용자 그룹, 드래그 핸들·아이콘, 구성원 관리 메뉴와 종합 상태 표현을 연결한다. 단순 표시 개선 등 다른 단계에 의존하지 않는 작업은 담당자 판단으로 앞당길 수 있다.
7. **세부 디자인 정돈과 변경 범위 검증:** 구조와 동작이 연결된 뒤 간격·색상·글자·문구를 다듬는다. 변경된 기능과 그 영향을 받는 기존 동작, 권한, 데이터 보존과 모바일 화면을 확인하고 결과를 정리한다.

하위 화면을 먼저 완성한 뒤 상위 데이터나 계산 방식 때문에 다시 만드는 순서를 피한다. 다만 조사·검증에서 잘못된 전제가 드러났을 때 필요한 수정을 막는 뜻은 아니다. 영향이 큰 결정과 연결 지점을 먼저 확인해 불필요한 재작업을 줄인다. 실제 실행 순서와 변경 이유는 구현 과정에 간결하게 남긴다.

## 1. 모듈 구성 드래그 핸들의 가시성 개선

- 사용자 의견: 모듈 구성에서 순서를 바꾸는 점 6개 드래그 핸들이 너무 흐릿해 잘 보이지 않는다.
- 기본 상태에서도 배경과 충분히 구별되도록 색상·대비를 조정하고, 잡아서 움직이는 조작부임을 쉽게 알아볼 수 있게 한다. 마우스를 올려야만 보이는 방식으로 처리하지 않는다.
- 상태: 반영 예정.

## 2. 모듈 정렬의 위·아래 화살표 제거

- 드래그 핸들과 용도가 겹치는 위·아래 화살표 버튼을 제거한다.
- 정렬 조작은 드래그 핸들로 통일한다. 핸들의 키보드 정렬과 터치 조작은 유지한다.
- 상태: 반영 예정.

## 3. ‘빼기’ 버튼을 아이콘으로 변경

- 모듈 구성의 ‘빼기’ 텍스트 버튼을 제거 의미가 분명한 아이콘 버튼으로 바꾼다.
- 아이콘에는 접근성 이름과 툴팁을 제공해 어떤 모듈을 목록에서 빼는지 알 수 있게 한다.
- 목록에서 빼도 기존 기록을 삭제하지 않는 동작은 유지한다.
- 상태: 반영 예정.

## 4. 모듈 분류·그룹 구조와 통합 분석의 연결

- 모듈을 용도에 따라 분류하고, 사용자가 분류를 직접 선택해 필요한 모듈을 찾을 수 있게 한다.
- 기본 분류는 함께 살펴볼 필요가 있는 기록과 지표의 관계를 기준으로 설계한다. 탐색 편의뿐 아니라 통합 상태에서 어떤 정보를 함께 분석할지까지 고려한다.
- 예를 들어 식사·간식·체중·활동 기록을 함께 검토해, 급여 패턴과 체중·활동 변화가 어떤 모습으로 나타나는지 종합 판단에 연결할 수 있다. 이는 설계 방향의 예시이며 최종 분류명이나 지표 조합을 확정한 것은 아니다.
- 검색어를 모르거나 정확한 모듈 이름을 기억하지 못해도 전체 목록을 하나씩 훑지 않고 탐색할 수 있게 한다.
- 모듈 구성의 ‘전체 모듈’ 영역에 분류 탐색을 제공하며, 검색도 함께 사용할 수 있게 한다. 전체 목록으로 돌아가는 경로를 명확히 둔다.
- 기본 분류는 모듈 구성과 바깥의 ‘돌봄 모듈’ 화면에 일관되게 적용한다. 사용자가 이름을 정하고 원하는 모듈을 묶는 사용자 그룹도 지원해, 모듈이 많을 때 자기 방식으로 정리할 수 있게 한다.
- 화면에서 정리하는 사용자 그룹과 통합 상태의 분석 관계는 구분한다. 사용자가 그룹 이름이나 배치를 바꿨다고 종합 판단의 의미와 기준이 달라지지 않도록 설계한다.
- 분석 영역별로 어떤 모듈·지표를 사용하고, 무엇을 함께 비교하며, 어떤 결과를 통합 상태에 전달할지 정한다. 한 모듈이 여러 분석에 필요한 경우 이를 고려하되 같은 사실을 중복 반영하지 않는다.
- 분류명과 모듈 배정, 탭·필터 등 표시 방식은 실제 모듈의 용도와 화면 공간에 맞춰 정한다.
- 상태: 반영 예정.

## 5. 기록 기반 종합 상태 판단 로직과 통합 화면 구현

- 사용자 의견: 현재 통합 상태는 모듈별 정보를 최대 4개씩 따로 보여주는 수준이다. UI만 바꾸거나 표시 항목을 늘리는 것으로는 요구를 충족하지 못한다. 기록을 함께 분석해 반려동물의 전반적인 상태를 볼 수 있어야 한다.
- 완성된 서비스는 상태 계산을 위해 외부 언어모델이나 생성형 AI API를 호출하지 않고, 구현한 분석 코드를 실행해 결과와 근거를 제공한다.
- 핵심 변경은 내부 분석 로직이다. 체중의 변화, 식사 간격·규칙성, 확인 가능한 급여량, 활동·휴식과 관찰 기록 등 여러 지표를 연결해 종합적인 상태를 도출한다. 개별 지표를 요약해서 나열하는 단계에서 끝내지 않는다.
- 4번에서 설계한 모듈·지표의 관계를 분석에 사용한다. 관련 기록을 함께 해석한 영역별 결과를 전반적인 상태와 설명에 연결한다. 분류별 카드에 숫자를 모아 보여주는 것만으로 통합 분석을 구현했다고 보지 않는다. 함께 변한 기록의 관계와 원인에 대한 확정 판단은 구분한다.
- 주된 종합 판단은 우리 반려동물의 실제 기록, 평소 패턴과 최근 변화에서 도출한다. 집단 평균보다 높거나 낮은지를 주화면의 중심으로 삼거나, 평균과의 차이로 종합 상태를 대신하지 않는다. 어떤 기록을 어떤 기간으로 집계하고 서로 어떻게 연결할지는 종합 판단의 목적에 맞춰 설계한다.
- 필요한 이론과 분석 방법은 구현 담당자가 직접 조사·비교하고, 실제 기록의 특성과 사용자 목적에 적합한 방식을 선택해 구현·검증한다. 선택한 방법의 적용 이유와 결과를 뒷받침하는 근거를 정리한다.
- 구현 전에 여러 접근 방식의 전제, 필요한 데이터, 장단점과 설명 가능성을 검토한다. 보기 좋은 결과를 먼저 정하고 계산을 끼워 맞추지 않는다. 사용한 이론·수치 기준의 출처와 적용 범위, 방법을 선택한 이유를 남긴다.
- 기록의 양과 누락, 개체별 평소 패턴, 관련 지표 간 관계와 변화, 시간에 따른 비교를 어떻게 처리할지 함께 설계한다. 특정 알고리즘이나 임의의 계수·문턱값을 기획 단계에서 미리 고정하지 않는다.
- 결과 화면은 전반적인 상태를 먼저 보여주고, 이를 이해하는 데 필요한 핵심 요소 몇 가지와 중요한 변화·이유를 함께 표시한다. 사용자가 개별 통계를 일일이 해석하지 않아도 현재 상황을 대략 파악할 수 있게 한다. 관련 기록·지표는 상세에서 확인한다. 임의로 모듈 네 개를 골라 보여주는 방식이나 모든 모듈의 긴 카드 나열로 종합 판단을 대신하지 않는다.
- 핵심 요소의 예시는 체중의 최근 추세, 식사 간격·규칙성, 활동·휴식 변화, 최근 관찰 내용이다. 모든 항목을 매번 표시하기보다 실제 기록에서 현재 상황을 설명하는 요소를 선정한다. 구체적인 지표 수나 문구는 아직 고정하지 않는다.
- 현재·7일 전·1개월 전의 종합 상태와 변화를 비교할 수 있게 한다. 비교 시 사용한 기간·기준을 일관되게 정의한다.
- 미기록을 실제 미급여·미활동이나 수치 0으로 간주하지 않는다. 기록 충실도와 반려동물 상태를 구분하고, 자료가 부족한 부분은 판단 근거가 부족하다는 점을 결과에 반영한다. 중요한 변화가 다른 정보에 묻히거나, 같은 사실이 중복 반영돼 판단을 과장하지 않도록 검토한다.
- 일반적인 식사·체중·활동 기록에서 필요한 정보를 계산해 활용한다. 종합 결과를 만들기 위해 사용자가 매번 긴 보고서를 추가 입력하게 하지 않는다.
- 구성원별 열람 권한을 유지하며, 제한된 기록의 내용이 종합 결과를 통해 다른 참여자에게 드러나지 않게 한다.
- 검증은 서로 다른 상태의 기록 조합이 실제로 다른 종합 결과와 설명을 만드는지 확인한다. 단순 카드 개수·배치 변경이나 개별 통계 합산만으로 완료 처리하지 않는다.
- 평소와 비슷한 기록, 한 지표만 변한 기록, 여러 지표가 함께 변한 기록, 상반된 신호, 기록 부족·누락과 경계 상황을 구분해 검증한다. 조사·적용 가능성 분석 → 방법 선정과 설계 → 계산·설명 로직 구현 → 기록 조합별 검증 → 화면 연결 순서로 진행한다.
- 상태: 내부 판단 로직 설계·구현과 결과 화면 재구성 예정.

## 6. 같은 분류의 평균·참고 기준 비교를 보조 기능으로 제공

- 사용자 의견: 대형견 등 같은 기본 분류의 평균과 자기 반려동물의 정보를 비교해 참고할 수 있으면 좋겠다. 이 기능은 기록 기반 종합 상태와 구분한 추가 요소다.
- 예를 들어 대형견으로 등록한 개의 체중 등을 적용 가능한 대형견 평균·참고 범위와 비교해 현재 위치를 확인할 수 있게 한다.
- 실제 비교값은 출처와 대상 조건을 확인한 자료를 사용하고, 평균과 참고 범위의 의미를 구분해 표시한다. 비교 자료를 확보하지 못한 항목에 임의의 평균을 넣지 않는다.
- API 연동은 필수 조건이 아니다. 개·고양이에 관한 공식 기준표, 문헌, 공개 데이터 등 적합한 자료가 있으면 출처와 적용 조건을 확인해 서비스의 기준 데이터로 정리하고 사용한다. 종·체격·품종 중 어떤 분류가 유효한지도 자료에 맞춰 검토하며, API 제공 여부로 활용 가능성을 제한하지 않는다.
- 평균보다 높거나 낮다는 사실과 건강 상태의 판정은 구분한다. 이 비교 결과 하나로 반려동물의 전체 상태를 결정하지 않는다.
- 5번 종합 상태는 이 비교 자료가 없어도 실제 기록에 근거해 사용할 수 있게 한다. 평균 비교는 필요할 때 추가로 확인할 수 있는 보조 정보로 배치한다.
- 상태: 보조 기능 설계·반영 예정.

## 7. 구성원 이름 옆 더보기 메뉴에서 권한 관리

- 사이드바에 표시되는 구성원 이름 옆에 `⋯` 더보기 메뉴를 두어 방장이 해당 참여자를 바로 관리할 수 있게 한다. 전체 구성원 화면에서도 같은 방식으로 관리할 수 있게 한다.
- 메뉴에서 관리자 지정, 관리자 권한 해제와 방에서 내보내기를 제공한다. 현재 역할에 맞는 동작을 표시하고, 변경 결과를 이름 옆 역할 표시에도 반영한다.
- 권한 지정·해제와 내보내기는 방장만 실행할 수 있게 한다. 기존 방별 권한 구조를 유지하고 다른 방의 권한에 영향을 주지 않는다.
- 구글 로그인으로 계정을 연결한 참여자만 관리자로 지정할 수 있다는 기존 조건을 유지한다. 로그인하지 않은 게스트에게는 관리자 지정에 계정 연결이 필요하다는 점을 알 수 있게 한다.
- 방장 자신에게 관리자 해제·내보내기 같은 잘못된 동작을 제공하지 않는다. 내보낸 참여자가 작성한 기존 기록은 보존한다.
- 상태: 반영 예정.

## 8. 돌봄 모듈·전체 기록의 배치와 공간 활용 재설계

- 사용자 의견: 앞서 요청한 화면 개선이 충분하지 않다. 특히 데스크톱에서 가로로 긴 행을 세로로 반복해 쌓아놓는 구조라, 각 항목 내부에 큰 공백이 남고 정보와 조작이 멀리 떨어져 있다. 모듈을 대부분 활성화한 경우 위에서 아래까지 계속 훑어야 해서 눈이 피로하고, 배열이 단조롭게 느껴진다.
- ‘돌봄 모듈’과 ‘전체 기록’ 화면 자체를 다시 디자인한다. 기존 긴 행을 유지한 채 색상이나 여백만 조금 바꾸는 것으로 완료하지 않는다.
- 데스크톱의 가로 공간을 실제 정보량에 맞게 활용하고, 관련 정보와 조작을 가까이 묶는다. 항목 수가 많아져도 큰 빈 행들이 반복되어 스크롤 길이만 늘어나지 않게 한다.
- 돌봄 모듈은 4번의 기본 분류·사용자 그룹과 연결해 필요한 활동을 쉽게 찾고 바로 사용할 수 있게 배치한다. 다열 구성이나 간결한 묶음 등 적합한 형식을 검토하되 모든 모듈을 큰 카드로 나열하는 방식으로 대체하지 않는다.
- 전체 기록은 시간순 이력을 빠르게 읽고 비교할 수 있는 정보 밀도를 갖추도록 재구성한다. 날짜·활동·핵심 내용·기록자가 가까이 읽히게 하고, 검색·필터와 상세 확인 흐름은 유지한다.
- 두 화면의 역할 차이는 유지한다. 돌봄 모듈은 활동별 관리·기록, 전체 기록은 과거 이력 탐색에 맞게 화면 구성을 달리한다.
- 공간 낭비를 줄이면서도 읽기 쉬운 글자 크기와 조작 간격을 유지한다. 장식이나 불필요한 정보를 채워 넣는 방식으로 공백을 해결하지 않는다.
- 소수 모듈을 쓰는 경우와 대부분을 활성화한 경우, 기록이 적은 경우와 많은 경우를 실제 화면에서 비교한다. 데스크톱에서는 불필요한 빈 폭과 시선 이동·스크롤을 줄였는지 확인하고 모바일 배치는 별도로 조정한다.
- 상태: 화면 구조 재설계·반영 예정.

## 9. 다수 정보를 다루는 UI·UX 조사와 모듈형 구조 보완

- 사용자 의견: 모듈형 구조에서는 사용자가 다뤄야 할 정보가 많아지고, 효과적인 배치와 보여줄 정보의 구분이 중요해진다. 현재 화면에서 드러난 불편을 계기로 모듈형 사이트 자체의 한계와 단점도 조사해 보완할 필요가 있다.
- 조사 목표는 ‘많은 정보를 효율적으로 배치하고, 사용자가 필요한 내용을 쉽게 찾아 이해하고 행동하게 하는 방법’이다. 모듈형 서비스를 우선 살펴보되 모듈형이라는 형식이나 반려동물 분야에 조사 범위를 한정하지 않는다.
- 운동·활동 관리, 일정·업무 관리, 기록·재고 관리, 분석 대시보드 등 여러 분야에서 정보 밀도, 분류·탐색, 요약과 상세의 연결, 상황에 따른 노출 방식을 비교한다. 유사한 외형보다 테일리에서 겪는 정보 처리 문제를 잘 해결하는지를 기준으로 참고 대상을 고른다.
- 모듈 수가 늘어날 때의 탐색·선택 부담, 설정해야 할 항목의 증가, 화면 간 중복 정보, 서로 떨어진 활동 흐름과 일관되지 않은 조작 등을 검토한다. 실제로 해당하는 문제와 가정을 구분한다.
- 관련 사용성·정보 설계 이론과 외부 서비스의 해결 방식을 폭넓게 조사하고, 테일리의 개인·공동 돌봄 상황에 적용할 수 있는 보완책을 선택한다. 조사 결과를 용어 소개나 사례 목록으로 끝내지 않고 실제 구성과 동작 개선에 연결한다.
- 사용자 목적에 따라 항상 필요한 정보, 시점·상황에 따라 나타날 정보, 요청할 때 보는 상세 정보와 설정을 구분한다. 노출 우선순위는 임의의 항목 수 제한이 아니라 사용 목적·현재 상태·행동 필요성을 기준으로 정한다.
- 사용자가 모든 모듈과 표시 옵션을 일일이 정리해야만 편해지는 구조인지 점검한다. 기본 구성 자체가 이해하기 쉽고, 필요한 경우에만 추가 조정할 수 있도록 한다.
- 4번 분류·그룹, 5번 종합 상태, 8번 화면 재설계와 함께 검토한다. 특히 정보량을 줄인다는 이유로 종합 상태의 핵심 판단을 숨기거나, 필요한 기능을 찾을 수 없게 만들지 않는다.
- 적은 모듈과 많은 모듈, 적은 기록과 누적된 기록, 방장·관리자·게스트, 데스크톱·모바일 상황에서 필요한 항목을 찾고 기록·상태 확인까지 도달하는 흐름을 비교한다. 불필요한 탐색·설정·반복 입력과 시선 이동이 줄었는지 확인한다.
- 블로그에는 실제 사용 중 정보량과 배치의 한계를 발견한 과정, 선택한 보완 방법과 적용 결과를 구분해 남긴다.
- 상태: 조사·설계 보완 및 반영 예정.

## 10. 루틴 날짜 선택·확인 영역의 가로 폭 축소

- 사용자 의견: 루틴에서 날짜를 확인하는 영역이 사이드바를 제외한 본문 너비를 거의 전부 차지할 정도로 길다.
- 날짜 입력과 확인·조회 버튼에 필요한 만큼의 간결한 폭으로 줄이고, 관련 조작을 가까이 묶는다. 넓은 화면에서 입력 영역이 불필요하게 늘어나지 않도록 한다.
- 날짜 선택·조회 기능은 유지하며, 좁은 화면에서도 입력과 버튼이 잘리지 않게 배치한다.
- 상태: 반영 예정.

## 11. 중복 이동 버튼 제거와 주요 동작 위치 조정

- 사용자 의견: ‘오늘 기록하기’와 ‘기록 이력 열기’는 다른 탭으로 이동하는 역할이어서 기존 탐색 메뉴와 겹친다. 해당 중복 이동 버튼을 제거한다.
- 실제 활동을 입력·저장하는 빠른 기록 기능이나 특정 기록의 상세 확인까지 없애는 의미는 아니다. 제거 대상은 위 이름으로 제공되는 중복 페이지 이동 버튼이다.
- ‘새 루틴’과 ‘모듈 구성’ 기능은 유지하되, 화면 오른쪽 위에 관련 내용과 멀리 떨어져 있는 배치를 바꾼다.
- 해당 기능을 사용하는 목록·제목·관리 영역 가까이에 배치해 내용 확인과 조작이 자연스럽게 이어지도록 한다. 구체적인 위치는 전체 UI 재설계와 함께 정한다.
- 상태: 반영 예정.

## 12. 기존 요구사항에 더해 전반적인 UI·UX 개선

- 앞의 11개 요구사항은 중요도가 높은 필수 개선 사항으로 그대로 유지한다.
- 명시된 항목을 반영하면서 사이트 전반의 사용 흐름과 UI도 함께 살펴보고, 추가로 발견한 불편을 개선한다.
- 구체적인 개선 방법과 작업 순서는 실제 구현 담당자가 조사와 사용성 판단에 따라 정한다.
- 전반적인 UI·UX 개선을 이유로 기존 요구사항을 축소하거나 대체하지 않는다.
- 상태: 추가 개선 예정.

## 13. 개·고양이 품종 선택과 체격·참고 자료 연결

- 개와 고양이의 품종 정보를 미리 준비하고, 반려동물 등록에서 한글·영문 이름으로 검색하거나 목록을 스크롤해 선택할 수 있는 구성을 검토한다.
- 사용자 제안: 품종을 선택하면 해당 정보에 맞춰 체격 분류를 자동으로 연결하고, 믹스·품종 미상은 직접 체격을 고르는 방식으로 처리하면 어떨지 논의했다.
- 품종별 크기 차이, 믹스와 품종 미상, 개와 고양이의 차이 등 세부 처리와 자동·수동 분류 기준은 구현 담당자가 자료와 실제 사용 흐름을 조사해 판단한다. 대화의 예시를 검증 없이 고정 규칙으로 만들지 않는다.
- API 제공 여부에 매이지 않고 적합한 기준표·문헌·공개 데이터를 활용한다. 품종 정보가 부족해도 등록과 기본 기록 기능을 사용할 수 있게 한다.
- 상태: 자료 검토·설계 판단 및 반영 예정.
