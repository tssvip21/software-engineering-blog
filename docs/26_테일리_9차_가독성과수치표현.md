2026-11-16 작업 기록. 사용자 검토 전 로컬 초안이며 GitHub 게시 승인이 아니다.

## 현재 확인 결과

전체 화면의 가독성, 수치 표시, 빠른 기록 배치와 루틴 완료 흐름을 구현했다. Windows의 SQLite·PostgreSQL 검사와 실제 브라우저 흐름을 확인했다. 기존 클라우드 재배포·HTTPS·정적 파일·실제 계정 로그인을 확인했다. 운영의 새 돌봄 기록 저장·수정은 실제 입력 자료 또는 검증 자료 생성 승인이 없어 실행하지 않았다. 실제 Mac 환경은 현재 연결되지 않아 완료로 세지 않는다.

몸무게의 기존 표시, 기록 원값, 집계식, 비교의 분모와 대상은 바꾸지 않는다. 존재하지 않는 포장 개수·개당 용량·실제 소비량을 만들지 않는다. 운영 DB와 로컬 시연 DB는 섞지 않는다.

## 1. 화면 전체의 읽기 기준

오늘·돌봄 기능·전체 기록·상세·최근 통계·개별 통계와 그래프·루틴·반복 알림·물품·재고·반려동물 상태·일반 설정·구성원·기능 설정을 확인했다. 같은 기준 데이터의 15개 화면 유형을 1440/375/1920px에서 전후 비교했다.

본문과 입력값은 16px, 라벨과 버튼은 15px, 보조 설명·기록 시각·단위는 14px를 기본으로 하되 상대 단위로 확대된다. 13px는 짧은 분류 표시와 바닥글에 제한한다. 제목·현재값·실행 버튼의 굵기와 대비를 구분하고, 오류는 색뿐 아니라 항목명과 문장으로 표시한다. 일반 텍스트 대비 4.5:1과 200% 확대에서 내용·조작이 가려지지 않는 기준을 참고했다.[1][2] 이것이 전체 접근성 인증을 뜻하지는 않는다.

모든 글자를 같은 크기로 키우거나 안내 문장을 늘리는 대안은 선택하지 않았다. 이전 화면의 고정 글자 크기가 새 규칙을 덮던 부분을 제거했고, 원기록·필터·설정 라벨처럼 눈에 덜 띄던 곳도 함께 고쳤다.

## 2. 수치 표현 기준

표시만 바꾸고 내부 값은 그대로 계산·보존한다. 사용자가 수정 창을 열면 입력했던 원값이 나오며, 반올림된 원기록과 날짜별 표에는 원래 값을 확인하는 경로를 둔다.

| 종류 | 기본 표시 | 예외와 기준 |
| --- | --- | --- |
| 실제 시간 | 소수 분 대신 시간·분·초 | 1.234분 → 1분 14초. 0과 1초 미만을 구분. 원래 분 값은 보존 |
| 질량·부피 | 수치 크기에 맞는 mg/g/kg·ml/L | 0.055kg → 55g. 1kg/1L 미만은 작은 단위가 우선. 포장 개수를 역산하지 않음 |
| 거리 | m 또는 km, 보통 소수 첫째 자리 | 작은 0이 아닌 값은 더 세밀한 단위·자릿수로 남김. 비교열·축에는 공통 단위 적용 |
| 몸무게 | 기존 표시 유지 | 몸무게가 아닌 먹이·재고 규칙을 일괄 적용하지 않음 |
| 개수·횟수·주기 | 실제 개수는 정수 | 기록일 평균의 비정수 값은 정수 사건 수로 바꾸지 않음 |
| 금액 | 천 단위 구분, 통화 표시 | 원·엔은 정수, USD/EUR 등은 최대 소수 둘째 자리. 서로 다른 통화를 합치지 않음 |
| 비율·변화 | % 또는 %p, 비교 대상과 기간 유지 | 분모가 0이면 임의 비율을 만들지 않음. 작지만 0이 아닌 차이는 보존 |
| 환경 | 현재 항목에 맞는 단위 | 섭씨의 부적절한 백분율·pH의 새 건강 판정 없음 |
| 약 용량 | 입력된 수치를 정확히 표시 | 편의를 위한 소수 축약으로 용량을 바꾸지 않음 |
| 날짜·기간 | 실제 기록 시각, 날짜와 비교 구간 | 기록 시각과 일정 날짜를 혼동하지 않음. 시간대의 기존 정책 유지 |

같은 표/그래프의 각 셀에 서로 다른 단위를 붙이는 대안 대신, 비교할 값 전체에 하나의 단위를 고른다. 일반 표시 자릿수는 단위별로 달리 두고, 반올림하면 0이 되는 작은 값에는 세밀한 표시 또는 '미만' 표기를 사용한다. 실제 0·미입력·기록 없음·계산 불가·제공량 기준 추정값은 원래 구분을 유지한다.

### 전체 기록 유형의 적용 목록

| 기록 유형 | 숫자 입력 또는 수치 정보 | 의미와 표시 예외 |
| --- | --- | --- |
| 먹이·급여 | 준 양 · 실제로 먹은 양 | 제공량·확인 섭취량은 g/kg/mg 등 같은 차원의 단위. 제품별 열량·제공/섭취 기준을 분리한다. |
| 간식 | 준 양 · 실제로 먹은 양 | 급여 횟수는 정수, 양은 질량·부피·개수의 원래 의미 유지. 열량과 비중은 기존 계산 조건 유지. |
| 물 관리 | 측정하거나 보충한 양 | 교체·보충 횟수와 실측 ml/L를 구분한다. 남은 물을 개체 음수량으로 만들지 않는다. |
| 배변 | 건수·날짜·상태 | 관찰 횟수는 정수. 기록하지 않은 날의 실제 발생을 0이라고 해석하지 않는다. |
| 산책 | 산책 시간 (분) · 이동 거리 | 분·초 또는 시간·분·초. 거리 m/km는 크기에 따라 선택하되 전후 비교와 그래프는 같은 단위. |
| 놀이 | 놀이 시간 (분) | 기록한 실제 시간은 분·초. 시간을 적지 않은 활동은 건수와 시간 미입력으로 구분. |
| 훈련 | 훈련 시간 (분) · 시도 횟수 · 성공 횟수 | 시간은 분·초, 시도·성공은 정수, 기존 성공률은 %·차이는 %p. |
| 체중 | 체중 | 몸무게의 기존 표시·정밀도를 유지. BCS는 직접 입력한 정수 점수다. |
| 위생·손질 | 건수·날짜·상태 | 관리 건수, 명시적으로 적은 물품 사용량과 단위. 개당 용량을 추측하지 않는다. |
| 미용 | 건수·날짜·상태 | 과거 손질 이력과 건수·날짜를 보존해 표시. |
| 생활공간 청소 | 건수·날짜·상태 | 청소 건수·장소·명시된 물품 사용량. 재고 소비는 원기록을 한 번만 반영. |
| 투약 | 처방·지시받은 용량 | 약 용량은 표시에서도 원래 숫자를 반올림하지 않는다. 실제 사용 재고와 일정 확인을 구분. |
| 특이사항 메모 | 건수·날짜·상태 | 기록 건수와 날짜·입력 메모. 새 점수나 상태 수치를 만들지 않는다. |
| 병원·예방접종 | 건수·날짜·상태 | 예약·다음 날짜는 날짜 정보로 유지. 없는 처방량이나 간격을 만들지 않는다. |
| 수면·휴식 | 관찰한 시간 (분) | 관찰한 시간만 분·초로 표시. 취침 알림 확인은 관찰 시간으로 바꾸지 않는다. |
| 사육환경 | 측정값 | 온도 절대 차이·습도 %p·조명 관찰 시간·pH 기존 의미 유지. 위치가 다른 값은 섞지 않는다. |
| 생활 변화 | 이전 기록의 알 개수 | 이전 알 개수 등은 정수 그대로. 기존 기록 유형과 발생 시각 보존. |
| 탈피·털갈이 | 건수·날짜·상태 | 관찰 건수·이전 진행 이력을 유지. 실제 사건과 날짜 차이를 구분. |

| 지출 | 금액 | 원·엔 정수, 달러 등 소액 단위 소수 둘째 자리, 천 단위 구분. 통화별로 분리한다. |

입력창은 원값과 단위를 유지한다. 빠른 카드·목록·상세·표·그래프·물품·재고·일정에서는 같은 표시 함수를 쓰되, 값의 의미와 집계 대상은 각각 유지한다. 세부 입력 목록은 `tmp/handoff/phase9/number-inputs.json`, 실제 표시 코드는 `care/display_values.py`에 있다.

## 3. 빠른 기록 배치

현재값을 제목 옆에 두고, 설정값과 실행 버튼은 그 아래에 모았다. 불필요한 세로 여백을 줄이되 같은 행의 버튼은 하단에 정렬한다. 열 수를 고정한 요구로 해석하지 않고, 가용 폭과 긴 제목·값에 맞춰 열을 정한다. 기존 시연 기록을 바꾸거나 새 설명·배지로 빈칸을 채우지 않았다.

## 4. 루틴의 완료 정책

추가 입력이 없어도 기존 검증을 통과하는 일정은 곧바로 완료 기록을 남긴다. 청소 대상·관리 항목·체중·관찰 메모처럼 필요한 값이 빠지면 항목명을 보여 주고 같은 화면의 입력창으로 연결한다. 모르는 급여량·산책 시간·약 용량을 만들어 넣지 않는다.

입력 취소와 검증 실패는 미완료 상태를 유지한다. 응답이 끊기면 같은 요청 번호와 본문으로 결과를 다시 확인한다. 성공한 뒤에만 완료 묶음을 펼쳐 옮겨진 항목과 원기록을 찾도록 안내한다. 물품 사용은 같은 활동 하나가 소비의 출처이며, 수정·취소도 같은 원장에서 반영한다.

실제 브라우저에서 루틴 입력창의 날짜·시각이 비워지는 문제를 발견했다. 시간대가 붙은 문자열을 HTML 입력값에 직접 넘기지 않고, Django 위젯이 현재 공간 시간대로 포맷하게 바꿨다. 또한 비공개 루틴의 직접 입력 주소에서 조회 권한을 다시 검사했다.

## 5. 실행 호환성과 보존

Windows 11 AMD64에서 실제 Docker Desktop의 Linux/amd64 엔진으로 PostgreSQL·Django·Caddy를 실행했다. 프로젝트 전용 볼륨과 루프백 포트를 사용하는 `scripts/local_compose.py`는 PowerShell 전용 명령을 요구하지 않는다. 원격 로그인 비밀값을 로컬 검사 환경으로 복사하지 않는다. 공식 이미지의 Linux amd64/arm64 목록과 셸 줄바꿈도 확인했다.[3]

Windows: `.venv\Scripts\python.exe scripts\local_compose.py up`

macOS 준비 명령: `python3 scripts/local_compose.py up`

상태: `python3 scripts/local_compose.py status` · 중지: `python3 scripts/local_compose.py stop`. Windows에서는 동일한 인수를 해당 Python 실행기에 전달한다. `down`도 볼륨을 삭제하지 않으며, 이 도구에는 자료 초기화 옵션이 없다. 공개 사이트 이용자는 브라우저만 필요하고 Docker를 설치할 필요가 없다.

**실제 Mac 검증은 미확인이다.** 연결된 PC는 Windows이고 기존 SSH 설정에서 Mac을 확인하지 못했다. 브라우저 연결 도구는 현재 대화의 브라우저 연결 환경이 없어 접근 오류를 반환했으며, 사용 가능한 연결 검색에서도 설치된 Mac/Safari 검사 환경을 찾지 못했다. 새 계정·유료 검사 서비스를 임의로 연결하지 않았다. Windows의 WebKit/Chromium 실행을 Mac Safari 결과로 쓰지 않는다.[4]

## 검증 근거

SQLite와 실제 PostgreSQL의 자동 검사 각각 467개, Chromium·Firefox의 브라우저 동작 30개와 화면·폭·확대 조건 90개를 확인했다. 전후 읽기 기준 검사는 별도 45개 화면 조건이다. 숫자 입력·저장·표시, 작은 값, 0, 누락, 환산 경계, 원값 재편집과 루틴 입력/취소/연타/응답 유실/재고를 포함한다. 테스트 수 자체를 사용성 실험 결과로 바꾸어 쓰지 않는다.

수정에 사용한 보리 화면과 별도로 고양이·앵무새의 1280/360px 및 긴 문구·빈 목록·낮은 화면 조건을 최종 검사했다. 실제 휴대전화와 실제 Mac을 확인한 것은 아니다.

근거: `tmp/handoff/phase9/verification.json`, `docker-validation.json`, `browser-results.json`, `before/`, `after/`, `delivery-state.json`. PostgreSQL에서 발견한 트랜잭션 밖 행 잠금 오류도 실제 조회 경로에서 수정하고 자동 트랜잭션에 감춰지지 않는 별도 회귀 검사로 확인했다.

물품에 개수 이름(통·봉지·팩 등), 하나에 든 양과 단위를 선택적으로 등록할 수 있다. 이 정보는 영양 계산의 한 조각 무게와 별도로 저장한다. 입고에서 포장 개수를 선택하면 당시 용량을 기준으로 기존 재고 단위로 환산해 한 번만 반영한다. 예를 들어 2kg 사료 두 봉지는 입고 2봉지·합계 4kg으로 보이며, 이후 55g을 급여하면 내용물 재고에서 55g만 줄어든다. 50개들이 패드 두 팩은 100개, 개수로 관리하는 75g 치약 두 튜브는 2튜브와 포장 기준 총 150g으로 구분한다.
