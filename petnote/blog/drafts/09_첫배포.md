# 첫 배포 — 로컬에서 쓰던 테일리를 외부 주소로 열기

2026-11-12 작업 기록 초안. 아직 검토·게시하지 않았다.

배포를 준비하면서 수업 자료의 조건을 다시 확인했다. 처음 만든 테일리는 Django와 SQLite로 로컬에서 실행했지만, 추가로 받은 첫 프롬프트 템플릿에는 PostgreSQL과 Docker Compose가 명시돼 있었다. 사용자는 배포 부분을 자료 기준으로 맞추라고 했다.

기존 화면을 다시 만들기보다는 Django에 PostgreSQL 설정을 추가하고, Caddy·Django·PostgreSQL 세 컨테이너를 묶었다. Caddy는 HTTPS와 정적 파일을 맡고 Django는 기존 화면과 기능을 처리한다. 운영 DB는 새로 만들고 로컬의 시연 자료는 가져가지 않았다.

구글 클라우드 무료 체험을 이용하기로 했다. AI는 처음에 남은 크레딧을 확인해 달라고 했고, 사용자는 기존 체험을 쓰는 전제로 진행하라고 했다. 실제 잔액은 확인하지 못했으며 유료 계정으로 전환하지 않았다. 테일리 전용 소형 VM과 네트워크를 만들고, 발표 후인 12월 13일 오전 9시에 VM이 정지하도록 설정했다.

Docker는 설치돼 있었지만 엔진이 꺼져 있어 처음에는 연결되지 않았다. Docker Desktop을 실행한 뒤 세 컨테이너가 정상 기동됐다. Google Cloud CLI의 PowerShell 실행 파일은 실행 정책에 막혔지만, 정책을 바꾸지 않고 설치된 `gcloud.cmd`를 사용했다. 서버에 파일을 옮긴 뒤에는 root 전용 경로로 일반 사용자 `cd`를 시도해 실패했다. 경로 권한은 유지하고 관리자 권한 명령에 절대 경로를 넘겨 해결했다.

PostgreSQL에서 기존 테스트 346개가 통과했다. 컨테이너를 다시 만들어도 가상 기록과 작성자·방 관계가 남아 있는지 확인했다. 외부 HTTPS 주소에서는 첫 화면·DB 상태·CSS가 정상 응답했고, PC와 모바일 크기의 Chromium에서도 화면 오류가 없었다. 매일 백업을 설정하고 첫 백업을 임시 DB에 복원해 보았다.

구글 로그인 설정에서는 사용자가 콜백 주소를 JavaScript 원본 칸에 넣어 오류를 만났다. 두 칸의 차이를 처음부터 분명히 설명하지 않은 안내 문제가 있었다. 원본에는 도메인까지만, 승인된 리디렉션 URI에는 `/auth/google/callback/`까지 입력하도록 정리했다.

이어 JSON 다운로드 위치 안내도 실제 콘솔과 달랐다. 공식 안내를 다시 확인하니 현재는 생성 창을 닫은 뒤 보안비밀을 다시 보여주지 않는다. 사용자가 클라이언트 ID와 보안비밀을 로컬 파일에 직접 넣고, AI는 값을 출력하지 않은 채 서버 환경 파일에 적용하는 방식으로 연결했다.

실제 연결 검사에서는 `redirect_uri_mismatch` 오류도 확인됐다. 사용자가 승인된 리디렉션 URI를 저장한 뒤에는 구글 로그인 화면으로 정상 이동했고, 직접 계정으로 로그인했다. 서버에서는 Google 계정 1개가 생성된 것을 확인했다. 당시 돌봄 공간과 기록은 아직 없었으므로 실제 사용자 입력 저장까지 확인했다고 쓰지는 않았다.

첫 공개 버전은 HTTPS로 연결한 클라우드 VM에 배포했다.

운영 명령과 백업 위치, 확인 결과는 `docs/21_배포와운영.md`에 정리했다. 웹 주소가 열린 것과 실사용 검증을 마친 것은 구분해 기록한다.
