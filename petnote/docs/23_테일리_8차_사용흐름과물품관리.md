# 테일리 8차 — 사용 흐름과 물품 관리

작성: 2026-11-14. 로컬 구현과 검수 결과이며 외부 공개·배포 기록이 아니다. 원래의 8차 요구와 사용자 피드백은 수정하지 않았다.

## 결과 요약

오늘·돌봄 기능에는 작업 내용 옆에 일정 패널을 두고, 반려동물 정보·개인/공동 설정·물품 관리의 역할을 나눴다. 기존 제품 ID, 돌봄 기록과 재고 계산을 재사용하므로 물품 목록을 새로 복제하거나 별도 소비 기록을 중복 생성하지 않는다. PC에서는 오른쪽 일정, 휴대전화 크기에서는 같은 내용을 상단에서 펼친다.

새 통계 지표나 건강 판정은 이번 작업에 넣지 않았다. 재고가 읽는 원기록 종류와 민감한 물품의 조회 권한 연결은 확장했지만, 체중·활동·급여 비교의 산술 정의는 그대로다.

## 설정창 조사와 선택 이유

공식 안내에서 개인 알림과 공동 공간 설정이 다른 적용 범위를 갖는다는 점, 설정을 바꿀 수 있는 역할을 구분하는 방식, 모달의 초점·닫기, 모바일에서 실제 보이는 화면 높이 변화 등을 확인했다.[1–4] 상용 앱의 로그인 내부를 직접 사용한 것으로 기록하지 않는다. 아래 항목과 권한은 테일리의 기존 기능을 재분류한 구현 결정이다.

| 항목 | 초기 표시·기본값 | 저장 위치 | 적용 범위·변경 권한 |
| --- | --- | --- | --- |
| 다가오는 일정 안내 표시 | 현재 개인 설정 유지; 새 참여자 기본 켬 | Membership.notices_enabled | 해당 공간의 본인 화면. 각 구성원 본인이 변경 |
| 기록 시간대 | 현재 공간 값 유지; 새 공간 Asia/Seoul | Room.timezone | 공간의 표시 날짜·루틴 계산. 방장·관리자만 변경 |
| 투약·병원·지출 기록 공유 | 현재값 유지; 새 공간 기본 제한 | Room.guest_sensitive | 공동 민감 기록과 해당 약품 재고. 방장만 변경 |
| 반려동물 이름·분류·생일·성장·체격 | 기존값 유지, 모르는 값은 비워 둠 | 기존 Room 동물 정보 필드 | 방장·관리자 변경, 일반 참여자는 읽기 전용 |

시간대 변경은 기존 활동의 절대 발생시각을 다시 쓰지 않는다. 과거 통계가 현재 공간 시간대로 묶이는 기존 특성까지 없앤 것은 아니며, 과거 시간대 이력을 새로 설계한 작업도 아니다. 개인 안내는 휴대전화 푸시 설정이 아니라 웹 안의 일정 안내 표시다.

체격 자동 제안을 회색 잠금값으로 만들지 않은 이유는 기존의 수동 예외를 보존해야 하고, 품종·성별·성장 단계만으로 모든 개체를 같은 체격으로 확정할 수 없기 때문이다. 기존 분류표를 제안으로만 쓰고 사용자의 값을 우선한다. 체격을 적정 체중이나 건강 진단으로 표시하지 않는다.

## 물품과 재고의 데이터 의미

기존 Product에 물품 분류와 선택 메모만 확장했다. 기존 사료·간식 ID와 영양 스냅샷을 그대로 두고, 비식품을 입력할 때는 영양 입력을 숨기며 서버도 해당 값을 저장하지 않는다. 일반 물품에는 이름·브랜드·종류·메모, 선택적인 재고 연결을 제공한다.

재고 연결은 품목 이름과 기준 단위를 명시한다. 등록만으로 잔량이나 사용량을 만들지 않으며 입고/실사는 기존 재고 기록에서 입력한다. 급여는 **제공량**, 위생·청소·투약 물품은 **직접 적은 실제 사용량**을 소비 근거로 삼는다. 사용량을 모르면 그 사실을 남기고 잔량을 완전한 실측값으로 표시하지 않는다. 약의 사용량 기록은 처방·복용량 추천이 아니다.

원기록의 제품과 당시 연결 정보가 소비의 출처다. 수정을 하면 같은 소비량을 다시 계산하고, 취소하면 같은 효과가 해제된다. 소비용 재고 행을 추가로 생성하지 않으므로 기록 두 번 전송·급여와 재고의 동시 반영에서 이중 차감하지 않는다. mg/g/kg, ml/L, 개수의 호환 여부를 확인하고 근거 없는 개수↔무게 변환은 하지 않는다.

민감한 약·영양제를 숨기는 설정은 물품 목록에서 끝나지 않는다. 재고 탭·전체 기록·원기록·수정 경로·통계에서도 같은 권한을 적용한다. 물품 이름이나 연결을 나중에 바꿔도 과거의 민감한 재고 이름이 노출되지 않게 기록 당시 연결을 유지한다.

## 검증과 실제 실패 수정

현재 자동 검사 **418개**, Chromium·Firefox의 실제 흐름 **28개**, 화면 폭·글자 확대·목록 조건 **76개**가 통과했다. 원본 시연 DB 대신 복사 DB를 사용했고, 물품 등록→재고 10개→2개 사용→3개로 수정→취소→10개 복귀를 실제 화면과 DB에서 함께 확인했다. 추가 소비 행이 생기지 않는지도 대조했다.

빈 물품 목록, 긴 이름·메모, 기존 보조 공간에 만든 32개 일정, 375px에서 접기/내부 스크롤, 키보드 이동, 오류·재시도와 설정 권한을 검사했다. 테스트마다 자료를 복제해 분리하고 일반 시연 예시를 늘리거나 원래 이름을 바꾸지 않았다.

첫 검사에서는 두 가지 문제를 발견했다. 기존 자동 검사 일부가 새벽 실행 때 '두 시간 전' 기록을 어제로 만들어 기대값과 어긋났다. 제품의 날짜 계산을 바꾸지 않고 검사용 시각을 정오에서 흐르도록 고정했으며, 자정 경계는 별도 검사했다. 또 낮은 화면에서 새 입력창이 직전 창의 세로 위치를 잠깐 유지하는 문제가 있어, 새 폼을 보여주는 즉시 크기와 위치를 다시 계산하도록 고쳤다.

물리적인 휴대전화 키보드·브라우저별 스크린리더·실제 보호자의 장기간 사용성은 확인하지 않았다. 브라우저의 VisualViewport 높이를 줄인 검사는 키보드가 차지할 공간을 모의한 것이지 실기기 검사가 아니다. 검사 통과를 사용자가 편해졌다는 실험 결과로 바꾸어 쓰지 않는다.

## 로컬 실행과 보존

로컬 확인 주소는 `http://127.0.0.1:8036`이며 아래 실행기는 **기존 시연 DB만 사용**한다. 예시 재생성·참고값 초기화·외부 호출은 하지 않는다. 필요한 데이터 구조 변경은 백업과 복사본 검증 후 별도 적용하고, 실행기는 미적용 구조가 있으면 시작 전에 알려준다.

```powershell
.\.venv\Scripts\python.exe -X utf8 scripts\run_workspace_preview.py --port 8036
```

8차의 최종 소스·검증·기존 레코드 보존 결과와 로컬 커밋은 `tmp/handoff/phase8/final-state.json`에, 진행은 같은 폴더의 `PROGRESS.md`에 남긴다. 전후 화면은 `before/`와 `browser/`에 있다. 변경 전 15개 사용자 작성 파일과 7개 DB의 돌봄 테이블을 기준으로 대조한다. 시연 DB에 추가되는 메모 열 외 기존 필드·기록은 유지하고 다른 원본 DB를 바꾸지 않는다.

이번 작업은 통계 산식 개편, 새로운 건강 판정, 백그라운드 GPS, OS 푸시, 외부 배포가 아니다. 사용자 문서·초안·그림과 기존 작업 중 변경은 이번 커밋에 섞지 않는다. GitHub와 클라우드에는 반영하지 않는다.

## 확인한 공식 자료

1. [Notion Workspace settings](https://www.notion.com/help/workspace-settings) — 공동 공간의 설정과 관리 권한을 구분하는 설명. 테일리의 항목·권한은 기존 서비스 정책에 맞게 별도로 정했다.
2. [Notion Notification settings](https://www.notion.com/help/notification-settings) — 개인의 알림 선택과 모바일 접근 경로. 외부 알림 채널은 이번에 추가하지 않았다.
3. [W3C Dialog (Modal) Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) — Tab·Shift+Tab·ESC, 창 내부 초점과 호출 위치 복귀 기준.
4. [MDN VisualViewport](https://developer.mozilla.org/en-US/docs/Web/API/VisualViewport) — 실제 보이는 높이·오프셋과 resize/scroll 이벤트. 키보드 공간 대응은 브라우저 모의와 실기기 결과를 구분했다.
