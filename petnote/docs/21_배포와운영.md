# 펫노트 배포와 운영

## 현재 운영 환경 · Vercel과 Supabase

[펫노트](https://petnote.duckdns.org/)는 Vercel에서 Django를 실행하고 Supabase의 PostgreSQL에 기록을 저장한다. 2026년 11월 24일 새 DB로 운영을 시작했다. 로컬 Docker Compose는 별도 실행 경로이며, 공개 Vercel 배포에 Docker 볼륨이나 로컬 시연 자료를 올리지 않는다.

Vercel의 기존 프로젝트는 `petnote`, 팀은 `petnote`다. 이 실행기는 애플리케이션만 모아 업로드하므로 프로젝트의 Root Directory 설정은 비워 둔다. Production에는 `DATABASE_URL`, `DJANGO_SECRET_KEY`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`을 Secret으로 등록하고 기존 값을 보존한다. DB 연결에는 Supabase Transaction pooler를 사용한다. `APP_ORIGIN`은 공개 HTTPS 주소, `DJANGO_ALLOWED_HOSTS`는 그 호스트 이름이며 Google 웹 클라이언트에는 `/auth/google/callback/`을 승인된 리디렉션 URI로 등록한다.

애플리케이션의 `.python-version`은 `3.13`으로 고정한다. Vercel, Docker와 CI에서 같은 Python 부버전을 사용한다.

### 바탕화면에서 서버 켜기·끄기

Windows 바탕화면의 **펫노트 서버 관리**를 열면 현재 공개 서버 상태가 표시된다. **서버 켜기**, **서버 끄기**, **상태 확인**, **펫노트 열기**를 사용할 수 있다. 프로그램을 닫거나 PC를 종료해도 Vercel의 켜짐·꺼짐 상태는 유지된다. 프로그램 실행 자체는 상태만 조회하며 서버를 자동으로 켜거나 끄지 않는다.

기존 Vercel CLI에 저장된 로그인을 재사용하고 인증 갱신은 공식 CLI에 맡긴다. 매번 웹 대시보드에 로그인할 필요가 없다. 인증이 취소되거나 갱신되지 않는 경우에만 **Vercel 다시 연결**이 표시된다. 해당 버튼으로 공식 로그인 창에서 연결을 완료한 뒤 **상태 확인**을 누른다. 이 도구는 비밀번호나 토큰을 별도 파일에 복사하지 않는다.

새 PC에서는 `petnote/` 폴더에서 `vercel link --project petnote --scope petnote`로 기존 프로젝트를 한 번 연결한다. 서버 관리 도구는 이때 로컬에 저장한 프로젝트 정보와 CLI 로그인을 사용한다.

끄기는 기존 펫노트 운영 프로젝트를 일시중지한다. 중지 중 공개 주소의 `503 / DEPLOYMENT_PAUSED` 응답은 정상이며, 켜기 후 같은 배포로 재개한다. DB 기록·환경 변수·요금제·로컬 Docker는 변경하지 않는다. 버튼을 누른 뒤 Vercel 상태와 공개 주소의 실제 응답을 함께 확인하므로 반영 중에는 잠시 기다린다. 요청이 지연되면 반복 클릭 대신 **상태 확인**을 사용한다.

바로가기를 다시 만들려면 프로젝트의 Python 환경에서 실행한다.

```powershell
.\.venv\Scripts\python.exe scripts/install_vercel_manager.py
```

터미널에서도 `scripts/vercel_control.py status`, `start`, `stop`을 같은 Python 환경으로 실행할 수 있다. 제어 대상은 이 프로젝트의 기존 팀·프로젝트 ID로 제한한다. 여러 창에서 중복 변경을 보내지 않도록 잠그며, API 원문·인증 정보는 화면과 로그에 출력하지 않는다. 기존 설치된 CLI를 우선 사용하고 누락된 경우 고정된 버전의 공식 CLI를 준비한다.

### 로컬 소스 확인과 단계 배포

Windows에서 Vercel CLI에 로그인한 뒤 애플리케이션 폴더에서 실행한다. 실행기는 설치된 CLI를 우선 사용하고, 없으면 Node.js의 `npx vercel@67.0.0`을 사용한다.

```powershell
npx.cmd --yes vercel@67.0.0 login
.\.venv\Scripts\python.exe deploy/deploy_vercel.py --package-only
.\.venv\Scripts\python.exe deploy/deploy_vercel.py
```

첫 번째 Python 명령은 외부 서비스에 연결하지 않고 소스 묶음만 만든다. 의존성의 원본은 `requirements.lock` 하나로 유지한다. Vercel의 중첩 요구 파일 해석 오류를 피하기 위해 전송할 `requirements.txt`에 잠금 파일의 바이트를 그대로 복사하며 로컬 원본은 변경하지 않는다. 원본 실행 파일에 추가 설치 지시가 생기면 누락시키지 않고 패키지 생성을 중단한다. 두 번째 명령은 기존 프로젝트·도메인·중지 여부를 확인한 뒤 `--prod --skip-domain`으로 운영용 배포를 준비한다. 운영 도메인을 옮기기 전에 해당 배포의 DB 상태, 첫 화면, 보안 응답 헤더와 정적 파일의 실제 해시를 검사한다. 배포 URL의 인증 보호는 유지한다. 소스 묶음을 기존 프로젝트에 로컬 연결한 다음 같은 폴더에서 로그인한 CLI의 `vercel curl`로 검사한다. 이 연결 정보는 임시 배포 폴더에만 남는다.

검증과 공개 전환을 한 명령에서 수행하려면 명시적으로 `--promote`를 사용한다.

```powershell
.\.venv\Scripts\python.exe deploy/deploy_vercel.py --promote
```

이 옵션은 새 운영용 배포를 준비하고 검사에 성공한 경우에만 `vercel promote`로 전환한다. 전환 후 공개 주소와 현재 운영 배포도 확인한다. 환경 변수 생성·수정, 비밀키 교체, DB 초기화는 수행하지 않는다.

배포 명령이 실패하거나 시간 초과로 끝나면 민감값을 가린 진단 출력을 해당 릴리스의 `logs/`에만 저장한다. API·환경 변수 조회·인증된 HTTP 응답은 이 로그에 저장하지 않는다.

배포별 소스 해시, Git 커밋, 이전·새 배포 URL, 검사 결과와 복구 명령은 `tmp/deploy/vercel/<시각-식별자>/release.json`에 저장된다. 업로드 전에 이 파일을 먼저 기록하므로 중단된 작업은 새 배포를 시작하기 전에 기록과 Vercel 상태를 대조한다. 기본 단계 배포만 수행했다면 이 기록의 `staged_deployment` URL을 확인한 뒤 프로젝트 연결이 남은 해당 릴리스의 `source/` 폴더에서 `vercel promote <URL> --scope petnote --yes`로 같은 배포를 전환할 수 있다.

### DB 변경과 복구

Vercel 빌드의 `deploy/vercel_build.py`는 운영 설정 검사와 `migrate --check`만 실행한다. 적용되지 않은 마이그레이션이 있으면 배포를 중단한다. 스키마 변경이 필요한 릴리스는 현재 DB 백업과 변경 계획, 이전 앱과의 호환성을 확인한 뒤 별도 관리 작업으로 적용한다. 빌드 재시도나 일반 재배포에서 `migrate`, `seed_references`를 자동 실행하지 않는다.

문제가 생기면 `release.json`에 기록된 이전 배포를 확인하고 `rollback_cwd` 폴더에서 `rollback_command`를 실행해 앱을 복구한다. 앱 롤백은 DB를 되돌리지 않는다. 운영 DB에 백업을 바로 덮어쓰거나 로컬 시연 자료를 넣지 않는다.

`503 / DEPLOYMENT_PAUSED`는 Vercel의 프로젝트 중지 상태다. 프로젝트 설정과 활동 기록에서 사유를 확인한 뒤 기존 프로젝트를 재개한다. 같은 오류에 DNS 변경·새 DB 생성·반복 재배포를 먼저 적용하지 않는다.

## 아래는 초기 배포 당시의 기록 (2026-11-12)

아래의 초기 도메인·VM 정지 기록은 당시 상황이며, 현재 서비스 주소와 확인 수준은 위의 최신 적용 상태가 우선한다. 초기 OAuth 주소는 보존된 등록값이다.


2026-11-12 배포. 수업의 첫 프롬프트 템플릿과 강의노트 08에 맞춰 PostgreSQL, Docker Compose, HTTPS를 구성했다. 기존 Django 화면과 기능은 유지하고 배포 구성을 추가했다.

**당시 실행 상태 (2026-11-12 전환):** 사용자 요청으로 클라우드 VM을 정지하고, 기존 시연 DB를 사용하는 로컬 웹 **http://127.0.0.1:8036**으로 전환했다. 실행 명령은 `.venv/Scripts/python.exe -X utf8 scripts/run_local.py --demo --profile record-actions --port 8036`이다. 클라우드 디스크·DB는 보존했으며 클라우드의 로그인·사용자 데이터를 로컬 시연 DB로 옮기지는 않았다. VM 정지 중에는 공개 사이트와 서버 내 자동 백업이 실행되지 않는다. 다시 시작할 때 외부 IP와 OAuth 주소를 확인한다.

## 공개 주소와 서버

- 접속 방식: VM의 외부 주소에 연결한 HTTPS 도메인
- Google Cloud 프로젝트: `YOUR_PROJECT_ID`
- VM 사양: 2GB 메모리
- 디스크: 20GB 표준 영구 디스크
- 네트워크: 전용 `taily-network` / `taily-subnet`
- 외부 공개 포트: 80, 443. 관리 SSH는 Google IAP 주소 범위에서만 허용한다.
- 무료 체험 크레딧 사용을 전제로 배포했다. 콘솔의 실제 잔액과 유료 계정 전환 여부는 직접 확인하지 못했다. 유료 전환 작업은 하지 않았다.
- VM 자동 정지: **2026-12-13 09:00 KST**. 12월 8일 발표 이후, 메일로 추산한 체험 만료일 이전이다. 정지는 디스크 삭제가 아니며 디스크는 남는다.
- 당시 주소는 VM의 외부 IP를 해석하는 sslip.io 이름이다. VM을 정지 후 시작해 IP가 바뀌면 앱 주소와 OAuth 리디렉션 URI를 함께 변경해야 한다. 별도 도메인은 구매하지 않았다.

## 세 컨테이너

| 이름 | 역할 | 저장 위치 |
| --- | --- | --- |
| frontend | Caddy의 HTTPS 인증서 발급·갱신, 정적 파일 전달, Django 프록시 | 인증서용 Docker 볼륨 |
| backend | 기존 Django HTML 렌더링, 입력·권한·통계, Waitress 실행 | 정적 파일용 Docker 볼륨 |
| db | PostgreSQL 16 | `taily_postgres_data` 볼륨 |

화면은 기존 Django 템플릿 방식이다. 별도의 React 앱으로 재작성하지 않았다. 프론트에서 같은 주소로 서버를 호출하므로 CORS 설정이 필요 없다. backend와 db의 포트는 호스트에 공개하지 않는다. Waitress는 공개 포트 없이 frontend 뒤에서만 실행하며, Caddy가 전달하는 HTTPS·클라이언트 IP 헤더를 해석한다.

운영 DB는 신규 생성했다. 로컬 SQLite와 시연 계정·기록은 옮기지 않았다. 기존 로컬 실행은 `POSTGRES_HOST`가 없으면 SQLite를 그대로 사용한다. 운영 컨테이너에서는 시연 로그인을 활성화하지 않는다.

## 실행과 재배포

로컬 확인에 사용한 환경 파일은 Git에서 제외되는 `tmp/deploy/local.env`에 있다.

```powershell
docker compose -f compose.production.yaml --env-file tmp/deploy/local.env -p petnote-verify up -d --build --wait
# http://127.0.0.1:8088
```

새 PC에서는 `deploy/production.env.example`을 참고해 환경 파일을 만든다. 로컬 확인은 `DJANGO_DEBUG=1`, `SITE_ADDRESS=http://:80`, `APP_ORIGIN=http://127.0.0.1:8088`, `HTTP_BIND=127.0.0.1`, `HTTP_PORT=8088`, `HTTPS_BIND=127.0.0.1`, `HTTPS_PORT=8448`을 사용하고 서로 다른 무작위 비밀키·DB 비밀번호를 생성한다.

```powershell
python scripts/package_deploy.py
gcloud.cmd compute scp tmp/deploy/petnote-source.tar.gz YOUR_VM_NAME: --project=YOUR_PROJECT_ID --zone=YOUR_ZONE --tunnel-through-iap
gcloud.cmd compute ssh YOUR_VM_NAME --project=YOUR_PROJECT_ID --zone=YOUR_ZONE --tunnel-through-iap
```

새 Docker 설치는 프로젝트와 DB 기본 이름으로 `petnote`를 쓴다. 기존 VM에서는 아래처럼 원래 설치 경로와 프로젝트 이름을 지정하고, 운영 환경 파일의 `POSTGRES_DB`와 `POSTGRES_USER`도 기존 값으로 유지한다. 기존 볼륨을 그대로 사용하기 위해서다.

```sh
sudo bash /opt/taily/app/deploy/backup-postgres.sh
sudo tar -xzf petnote-source.tar.gz -C /opt/taily/app
sudo docker compose --project-directory /opt/taily/app --env-file /opt/taily/production.env -p taily up -d --build --wait
```

패키지에는 애플리케이션·정적 파일·배포 스크립트만 넣는다. `.env`, 로컬 DB, 백업, 블로그, 과제 PDF는 넣지 않는다. 이미지 식별자와 Python 패키지 버전은 고정했다. DB 마이그레이션·기준 자료 등록·정적 파일 수집은 backend 시작 시 실행한다. 한 대·한 backend 기준이며 다중 서버용 배포 절차가 아니다.

## 구글 로그인

- OAuth 클라이언트 유형: 웹 애플리케이션
- 원본 예시: `https://petnote.example.org`
- 승인된 리디렉션 URI: `https://petnote.example.org/auth/google/callback/`
- 범위: `openid email profile`
- 운영 환경 파일: `/opt/taily/production.env` (root 전용 0600)

사용자가 콘솔에서 클라이언트를 생성하고 ID·보안비밀을 로컬 입력 파일에 직접 저장했다. 다음 명령은 값을 출력하지 않고 운영 환경 파일에 반영한다.

```powershell
.venv/Scripts/python.exe scripts/configure_google_oauth.py tmp/deploy/oauth-input.env
# JSON을 받은 경우 첫 번째 인수로 JSON 경로를 줄 수도 있다.
```

운영 파일을 IAP SCP로 전송한 뒤 `sudo install -m 0600`으로 설치하고 Compose를 다시 실행한다. 비밀값은 Git이나 블로그에 넣지 않는다. 구글은 생성 완료 창을 닫은 후 보안비밀을 다시 보여주지 않는다. 저장하지 못한 경우 클라이언트 상세의 보안비밀 추가 기능을 사용한다.

## 백업과 상태 확인

- 매일 **12:00 KST (03:00 UTC)** `taily-backup.timer`가 PostgreSQL 사용자 데이터와 스키마를 custom-format dump로 저장한다.
- 위치: `/var/backups/taily/taily-날짜.dump`와 SHA-256 파일. 서버 디스크에 보관한다.
- VM 디스크 자체의 손실에 대비하려면 중요 시점의 백업을 별도 위치에도 내려받아야 한다. DB 백업에는 OAuth 설정과 Django 비밀키가 포함되지 않는다.
- 배포 직후의 첫 백업은 사용자 PC의 `backups/taily-first-20261112.dump`에도 보관했다. 이후 자료는 서버의 매일 백업에 포함된다.
- 복원 검증: `sudo bash /opt/taily/app/deploy/verify-backup.sh`. 새 임시 DB에만 복원·검사한 뒤 그 임시 DB를 삭제한다.

```sh
sudo docker compose --project-directory /opt/taily/app --env-file /opt/taily/production.env -p taily ps
sudo docker compose --project-directory /opt/taily/app --env-file /opt/taily/production.env -p taily logs --tail 80 backend
sudo systemctl list-timers taily-backup.timer
curl --fail https://petnote.example.org/health/
```

데이터를 보존하려면 `docker compose down -v`를 사용하지 않는다. 운영 DB에 과거 백업을 덮어쓰는 복원은 서비스를 멈추고 현재 DB를 먼저 백업한 뒤 별도로 진행한다.

## 확인 결과

- PostgreSQL에서 기존 테스트 **346개 통과**.
- DB 마이그레이션 변경 없음, 패키지 의존성 검사 통과.
- 가상 기록·작성자·방 관계가 컨테이너 재생성 후 보존됨을 확인했다. 가상 검증 자료는 로컬 검증 DB에서만 만들고 검사 후 삭제했다.
- HTTPS 인증서 검증, `/`, `/health/`, CSS 응답 200, HTTP→HTTPS 308 확인.
- Chromium 1440px·390px에서 자바스크립트 오류와 가로 넘침 없음.
- 첫 운영 백업을 별도 DB에 복원해 마이그레이션 21개와 기준 자료 2개 확인.
- `check --deploy`에는 HSTS 하위 도메인 포함·브라우저 preload 미설정 경고 2개가 남는다. 이 도메인의 모든 하위 도메인을 운영하거나 preload 등록을 하는 구성이 아니므로 두 옵션을 켜지 않았다.
- OAuth 연결 검사에서 처음에는 `redirect_uri_mismatch`가 나왔다. 사용자가 승인된 리디렉션 URI를 저장한 뒤 구글 로그인 화면으로 정상 이동했다.
- 사용자가 실제 구글 계정으로 로그인했고 운영 DB의 Google 계정 1개를 확인했다. 이때 돌봄 공간 0개·기록 0개였으므로 실제 사용자 입력 저장까지 확인했다고 기록하지 않는다. 입력·권한 검사는 앞의 PostgreSQL 테스트로 확인했다.
