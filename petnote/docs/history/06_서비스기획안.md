# 반려동물 돌봄 관리 서비스 기획안

반려동물 돌봄 관리 서비스의 목표, 기능, 사용 흐름과 화면 구상을 함께 정리하는 기획안이다. 논의하면서 새로운 아이디어와 결정 사항을 계속 추가한다.

기획 논의: 2026-11-03. 1차 구현 상태 반영: 2026-11-04. 아래의 기획 구상과 실제 구현의 차이는 [구현과 실행](07_구현과실행.md)에서 확인한다.

## 1. 사용자가 정한 방향

- 개인 또는 여러 사람이 반려동물을 관리한다. 기본 단위는 반려동물 한 마리의 방이다.
- 모듈은 아래 20개로 구성한다. 식사와 간식, 위생과 미용은 각각 분리한다.
- 로그인은 구글 계정을 사용한다. 로그인한 사용자가 방을 만든다.
- 참여자는 초대 링크로 들어온다. 초대받은 사람은 가입하거나 구글 로그인하지 않아도 게스트로 돌봄 상태를 입력할 수 있다.
- 권한은 방장, 방장이 권한을 준 로그인 사용자, 링크로 들어온 게스트의 3단계다.
- 관리자가 되려면 구글 로그인이 필요하고 방장이 권한을 부여해야 한다. 로그인만으로 관리자 권한이 생기지는 않는다.
- 게스트는 돌봄 상태를 입력할 수 있지만 모듈 구성은 수정할 수 없다.
- 각 모듈에 독립적인 기록란과 상세 통계 화면을 둔다.
- 통합 상태 창은 현재·7일 전·1개월 전 등의 전체 상태를 핵심만 요약해서 보여준다. 세부 내용은 해당 모듈 요약을 눌러 상세 통계에서 확인한다.
- 종과 소형·중형·대형 같은 기본 분류에 맞는 평균·참고 기준과 반려동물의 상태를 비교한다. 과거의 자기 상태와 비교하는 기능도 함께 둔다.

아래의 상세 입력 항목, 화면 배치와 세부 권한 중 제안으로 표시한 부분은 AI가 추가한 아이디어다. 사용자가 직접 정한 방향과 구분한다. 기술 스택, 서비스 이름, 종별 비교 수치는 아직 미정이다.

## 2. 모듈 20개

모든 모듈에 해당 방, 기록자, 실제 활동 시각, 작성 시각, 메모를 연결한다. 실제 수행자가 기록자와 다르면 따로 표시할 수 있다. 사진·첨부는 후속 확장이 가능하도록 생각하되, 첫 구현에서 업로드를 지원하지 않으면 지원하는 것처럼 보이지 않게 한다.

| --- | --- | --- | --- |
| 1 | 식사 | 제품·먹이, 제공량, 단위, 확인 가능한 실제 섭취량, 시간 | 최근 급여, 일별 급여 횟수·양, 확인 가능한 영양 합계 |
| 2 | 간식 | 제품, 양, 단위, 시간, 급여 이유 선택 | 식사와 구분한 간식 내역, 전체 급여 합계 |
| 3 | 물 관리 | 보충·교체·음수 측정 구분, 물그릇, 측정량·단위 | 마지막 교체, 실제로 측정한 음수량; 보충량을 음수량으로 계산하지 않음 |
| 4 | 배변 | 대변·소변 구분, 시간, 관찰 상태, 특이사항 | 횟수와 관찰 기록, 기간별 변화 |
| 5 | 산책 | 시작·종료, 시간, 거리, 담당자 | 산책 중 표시, 일별·기간별 시간과 거리 |

| 7 | 훈련 | 훈련 항목, 시간, 시도·성공 횟수 선택, 메모 | 항목별 연습 기록과 진행 상황 |

| 9 | 위생 | 목욕·양치·귀 세정·발 세정 등 작업, 수행 시각 | 항목별 마지막 관리일과 예정 일정 |
| 10 | 미용 | 빗질·털 손질·발톱 관리 등 작업, 수행 시각 | 관리 이력과 다음 일정 |
| 11 | 생활공간 청소 | 화장실·케이지·수조·침구 등 대상, 청소 내용 | 대상별 최근 청소와 반복 일정 |

| 13 | 상태 관찰 | 식욕·행동 등 관찰 항목, 관찰 내용, 시각 | 변화의 시간순 기록; 자동 질병 판정은 하지 않음 |
| 14 | 병원·예방접종 | 진료·접종 구분, 예정·방문 날짜, 기관명 선택, 내용 | 예약과 완료 이력, 다음 일정 |
| 15 | 수면·휴식 | 관찰한 시작·종료 또는 시간, 수면·휴식 구분 | 관찰 범위 내 패턴; 미기록 구간을 수면으로 채우지 않음 |

| 17 | 발정·산란 | 발정 관찰·산란 구분, 날짜, 알 개수 선택, 메모 | 해당 동물에 필요한 생식 관련 관찰 이력 |
| 18 | 탈피·털갈이 | 탈피·털갈이 구분, 시작·종료, 진행 상태 | 진행 중 여부와 과거 기간 |
| 19 | 용품·재고 | 품목, 입고·사용·수량 조정, 수량·단위, 사용자 지정 최소 수량 | 잔량과 구매 필요 표시; 식사 기록과 재고 자동 차감은 후속 후보 |
| 20 | 지출 | 지출 항목, 날짜, 금액, 통화, 분류, 메모 | 사료비·병원비·용품비 등 기간별 합계; 통화가 다르면 별도 집계 |

### 모듈 설계 원칙

- 20개를 고를 수 있는 목록을 만들고, 사용자가 필요한 것만 켠다. 모듈 수를 채우기 위해 같은 기능을 이름만 바꿔 중복 구현하지 않는다.
- 식사와 간식은 화면과 기록 종류를 구분하되 제품 정보와 영양 계산은 공유한다. 위생과 미용도 별도 모듈이다.
- 각 모듈에 기록 입력·목록·상세와 별도의 통계 화면을 둔다. 모듈에 따라 필요한 입력, 핵심 수치, 상세 그래프가 달라진다.
- 모든 기록을 완료 체크 하나로 처리하지 않는다. 체중은 측정값, 지출은 금액, 재고는 수량 변동, 투약은 예정과 실행 구분이 필요하다.
- 모듈 비활성화는 화면에서 숨기고 새 루틴 실행·알림을 중단하는 동작이다. 기존 기록과 집계를 지우지 않는다.
- 상태 입력은 새로운 돌봄 활동이나 관찰 기록의 추가를 뜻한다. 반려동물 프로필이나 모듈 설정 수정과 구분한다.
- 체격·수명·식단 등 종별 전문 기준을 임의로 채우지 않는다. 참고 기준이 없는 항목도 기록과 추이는 사용할 수 있다.

### 종별 초기 구성 아이디어

처음에는 기존 기획대로 강아지는 산책·식사·간식, 고양이와 앵무새는 식사·간식을 기본으로 켜고 아래 모듈을 추가 후보로 보여줄 수 있다. 종만으로 모든 동물에게 필요한 관리가 같다고 단정하지 않고, 등록할 때 방장이 선택하게 한다.

- 강아지: 물 관리, 배변, 놀이, 체중, 위생, 병원·예방접종.
- 고양이: 물 관리, 배변, 놀이, 체중, 생활공간 청소, 위생.
- 앵무새 등 조류: 물 관리, 생활공간 청소, 놀이, 훈련, 체중, 상태 관찰.
- 파충류·양서류: 사육환경, 생활공간 청소, 체중, 상태 관찰, 해당 종의 탈피·산란 기록.
- 그 밖의 동물: 전체 목록에서 직접 선택. 특정 종에 맞지 않는 모듈을 강제로 넣지 않는다.

## 3. 방과 참여자의 권한

권한은 계정 전체가 아니라 방마다 부여한다. 한 사람이 자기 방에서는 방장이고 다른 방에서는 관리자 또는 게스트일 수 있다. 방장은 방당 한 명으로 시작하며, 방장 이전은 후속 기능으로 둔다.

| 기능 | 방장 | 관리자 | 게스트·로그인한 일반 참여자 |
| --- | --- | --- | --- |
| 방 참여 | 구글 로그인 후 생성 | 초대 링크 참여, 구글 로그인, 방장 지정 | 유효한 초대 링크로 참여; 구글 로그인 선택 |
| 방의 반려동물 정보·돌봄 기록 조회 | 가능 | 가능 | 가능 |
| 활성 모듈의 돌봄 기록 추가 | 가능 | 가능 | 가능 |
| 본인 작성 기록 수정·취소 | 가능 | 가능 | 허용 제안; 방장이 잠그는 기능은 후속 후보 |
| 다른 사람 기록 수정·취소 | 가능 | 가능 제안 | 불가 |
| 모듈 추가·끄기·순서·입력 설정 변경 | 가능 | 가능 | 불가 |
| 반려동물 기본 정보 변경 | 가능 | 가능 제안 | 불가 |
| 공용 루틴 생성·편집 | 가능 | 가능 제안 | 불가; 배정된 활동의 완료 입력은 가능 |
| 초대 링크 생성·폐기, 참여자 내보내기 | 가능 | 불가로 시작 제안 | 불가 |
| 관리자 지정·해제 | 가능 | 불가 | 불가 |
| 방 삭제 | 가능 | 불가 | 불가 |

게스트가 열람할 수 있는 범위는 기본적으로 해당 방의 반려동물 정보와 돌봄 기록이다. 계정 이메일, 초대용 비밀값, 로그인 정보는 보여주지 않는다. 지출·병원 자료를 게스트에게 별도로 숨기는 기능은 검토 후보이며, 참여자에게 보이는 범위를 명확히 안내하는 방향이다. 확정되지 않은 세부 권한은 위 표의 제안으로 남겨둔다.

### 초대와 승격 흐름

1. 방장이 구글 계정으로 로그인하고 반려동물 방을 만든다.
2. 방장이 초대 링크를 만들어 복사한다. 만료 시각, 사용 가능 횟수는 선택 설정 후보다.
3. 초대받은 사람이 링크를 열면 참여 안내와 표시 이름 입력 화면이 나온다. 링크만 열었다고 기록을 쓰거나 자동 참여시키지 않고 `참여하기`로 의사를 확인한다.
4. 가입 없이 게스트로 참여하고 해당 방의 기록을 확인하거나 추가한다.
5. 관리 권한이 필요하면 구글 로그인한다. 첫 로그인 시 필요한 회원 정보가 생성되는 방식으로 별도 가입 절차를 줄인다.
6. 기존 게스트 세션을 확인해 그 참여 이력과 계정을 연결한다. 방장은 해당 로그인 사용자를 확인하고 관리자로 지정한다.
7. 관리자를 해제하면 방의 일반 참여자로 남는다. 방에서 내보내는 동작은 별개다.

화면상 역할은 방장·관리자·게스트로 이해하기 쉽게 표현하되, 내부에서는 `로그인 여부`와 `방 권한`을 분리한다. 로그인한 일반 참여자에게 관리자 권한을 자동으로 주지 않는다.

### 게스트를 구분하는 방식

- 표시 이름은 사용자에게 보이는 이름이며 신원 확인 수단이 아니다. 같은 이름을 입력했다고 기존 사람의 기록이나 권한을 넘기지 않는다.
- 서버가 게스트 참여자와 세션을 식별하고 작성 기록에 연결한다. 브라우저에서 보낸 이름이나 역할 문자열만으로 권한을 인정하지 않는다.
- 게스트를 계정에 연결할 때는 현재 게스트 세션과 구글 로그인이 모두 확인돼야 한다. 이름·이메일 추정만으로 병합하지 않는다.
- 다른 기기나 쿠키 삭제 후에는 같은 게스트로 자동 복구되지 않을 수 있다. 이력 유지가 필요하면 구글 로그인을 선택하게 한다.
- 초대 링크로 받는 기본 권한은 게스트다. 링크를 바꾸거나 쿼리 값을 수정해서 관리자 권한을 얻을 수 없어야 한다.
- 초대 링크 폐기는 이후 참여를 막는다. 이미 참여한 사람의 접근을 끊으려면 별도로 내보내며, 해당 세션의 접근도 차단한다.
- 내보낸 사람이 아직 유효한 공용 링크로 다시 들어올 수 있으므로 `내보내기 + 기존 링크 폐기`를 함께 할 수 있게 제안한다. 무로그인 참여에서는 동일 인물의 재가입을 완전히 식별할 수 있다고 약속하지 않는다.
- 생성·수정·조회 요청에서 방과 참여 권한을 서버가 확인한다. 화면에서 버튼을 숨기는 것만으로 권한 제어를 구현하지 않는다.

## 4. 화면 초안

모바일에서 빠르게 한 건 기록하는 흐름을 우선한다. 데스크톱에서도 같은 기능을 사용할 수 있게 한다.

1. **시작·로그인:** 구글로 시작하기, 서비스 설명. 초대 링크 방문자는 게스트 참여 화면으로 바로 연결한다.
2. **내 반려동물 방:** 참여 중인 방 카드, 이름·사진·종·내 권한, 새 방 만들기. 게스트는 현재 세션에서 참여한 방만 표시한다.
3. **반려동물 등록:** 이름과 종을 우선 입력하고 체중·생년월일·체격 등은 필요한 것만 추가한다. 모르는 값은 비워 둘 수 있다. 기본 모듈을 선택한다.
4. **오늘:** 반려동물 요약, 진행 중인 활동, 오늘 일정, 활성 모듈 카드, 최근 기록. `식사 기록`, `산책 시작`처럼 바로 입력하는 버튼을 둔다.
5. **모듈 목록·설정:** 20개 모듈을 분류해서 찾고 켜거나 끈다. 공용 표시 순서는 관리자 이상만 바꾼다. 게스트는 사용 중인 모듈을 열어 기록한다.
6. **기록 입력·상세:** 최소 필수 항목부터 보여준다. 저장 후 오늘 화면과 목록에 반영하고, 실패하면 입력 내용을 유지한다. 자신에게 없는 수정 권한은 표시하지 않는다.
7. **전체 기록:** 날짜·모듈·기록자별 필터와 시간순 목록. 수정·취소 여부를 확인한다.
8. **루틴:** 반복 요일·예정 시간·담당자·활동 구성, 오늘의 실행 상태. 게스트도 허용된 활동을 완료할 수 있다.
9. **모듈별 통계:** 각 모듈의 수치, 기간별 변화, 상세 그래프와 관련 기록. 통합 상태 창에서 해당 모듈을 눌러 들어오거나 모듈 안에서 직접 연다.
10. **통합 상태:** 현재·7일 전·1개월 전 등의 전체 상태와 분류별 기준 대비 위치를 핵심만 요약한다. 세부 기록과 복잡한 그래프는 펼쳐놓지 않고 모듈별 상세 통계로 연결한다.
11. **구성원·초대:** 내 역할, 참여자 이름과 로그인 여부, 초대 링크 복사, 승격·해제·내보내기. 방장 전용 조작을 구분한다.
12. **방 설정:** 반려동물 정보, 시간대, 모듈과 루틴 설정 진입, 방 삭제. 게스트에게는 읽기 가능한 정보와 나가기만 제공한다.

처음 만든 방, 기록 없는 모듈, 만료된 링크, 접근이 끊긴 방, 저장 실패도 정상적인 화면 상태로 설계한다. 빈 화면을 시연 데이터로 채워 실제 기록처럼 보이게 하지 않는다.

## 5. 공통 동작과 데이터 구조 아이디어

### 기록과 루틴

- 공통 기록에는 방, 모듈, 작성자, 실제 수행자 선택, 실제 활동 시각, 상태, 메모, 작성·수정 시각을 둔다. 기록 수정·취소는 이력을 남기고 집계를 갱신한다.
- 모듈별 상세는 필드 정의에 따른 값으로 저장하되, 숫자·단위·필수값·선택값을 서버에서도 검증한다. 단순 자유 텍스트 하나로 20개를 대신하지 않는다.
- 예정된 일과 실제 기록을 구분한다. 루틴에서 완료해도 활동 기록은 한 번만 생성하며, 모듈에서 생성한 기록도 같은 루틴 실행에 연결할 수 있다.
- 같은 저장 요청의 재전송이나 같은 루틴 항목에 대한 동시 완료는 중복 반영을 막는다. 독립적으로 일어난 두 번의 급여는 서로 다른 기록으로 허용한다.
- 진행 중인 산책 등은 시작 상태를 먼저 저장하고 종료 시 갱신한다. 예정만 된 활동은 완료 통계에 넣지 않는다.
- 모듈 숨김, 참여자 퇴장, 제품 정보 변경이 과거 기록의 의미를 바꾸지 않게 한다. 영양 계산에 사용한 값은 당시 값을 보존한다.
- 날짜별 요약은 방의 시간대를 기준으로 묶고 실제 시각 저장 방식은 일관되게 정한다. 초안 기본 시간대는 Asia/Seoul을 제안한다.

## 6. 추가로 떠오른 아이디어

아래는 확정 범위가 아닌 후보 목록이다. 첫 초안에 전부 집어넣기보다 핵심 흐름이 완성된 뒤 선택한다.

- **입력 편의:** 최근 제품·급여량 재사용, 자주 쓰는 값 선택, 현재 시각 기본값, 과거 기록 입력, 입력 중 닫기 확인.
- **공동 돌봄:** 누가 언제 입력했는지 표시, 진행 중 활동 표시, 최근 식사 확인, 게스트에게 특정 루틴 담당 배정.
- **초대 편의:** QR 코드, 만료 시간·최대 참여 횟수, 링크 재발급, 로그인 후 관리 권한 요청 버튼.
- **맞춤 구성:** 모듈 검색과 분류, 종별 추천 묶음, 카드 크기 선택, 개인별 표시 필터. 방 공용 설정과 개인 취향을 구분한다.
- **회고와 공유:** 특정 기간 기록 내보내기, 병원 방문용 요약, 사진과 메모 묶음. 내보내기 권한과 포함 자료는 별도 결정한다.
- **재고 연결:** 식사·간식 기록으로 제품 재고 차감, 구매 기록에서 재고 입고. 취소·수정 때 되돌리는 처리가 준비된 뒤 연결한다.
- **지출 관리:** 영수증 첨부, 품목별 합계, 정기 구매. 결제·송금 기능은 포함하지 않는다.
- **알림:** 앱 내부 일정 표시부터 시작해 브라우저 알림·이메일을 후속 검토한다. 야간 알림 제한과 참여자별 수신 설정도 후보로 둔다.
- **접근성:** 큰 입력 버튼, 숫자·단위가 분명한 폼, 색만으로 상태를 구분하지 않기, 좁은 화면에서도 표 대신 읽기 쉬운 카드 사용.
- **장기 확장:** 여러 마리 그룹 관리, 활동 일괄 기록, 돌봄 인수인계, 사용자 정의 모듈. 기존 계획대로 다음 버전 후보로 유지한다.

## 7. 모듈별 기록·통계와 통합 상태 확인

### 각 모듈의 기록란과 상세 통계

20개 모듈 각각에 해당 활동이나 상태를 입력하는 기록란과 이전 기록을 확인하는 목록을 둔다. 각 모듈의 통계 화면에서는 관련 수치, 기간별 변화와 상세 그래프를 확인한다. 예를 들어 식사에서는 급여 기록과 섭취량을, 산책에서는 시간·거리를, 체중에서는 측정값과 변화를 자세히 본다.

### 통합 상태 창은 전체 흐름만 간결하게

통합 상태 창은 여러 모듈의 정보를 모아 반려동물의 전체 관리 현황을 거시적으로 보는 화면이다. 현재 상태, 7일 전 상태, 1개월 전 상태 등을 함께 비교해 무엇이 달라졌는지 파악한다.

각 모듈은 핵심 수치, 변화 방향, 참고 기준 대비 위치 정도만 간략하게 표시한다. 모든 상세 수치나 개별 기록, 복잡한 그래프를 한 화면에 펼쳐놓지 않는다. 여러 정보를 종합한다는 뜻이지 체중·급여량·산책 거리처럼 단위와 의미가 다른 값을 하나의 총합으로 더한다는 뜻은 아니다.

통합 상태 창에 간략하게 표시된 모듈 요약을 누르면 해당 모듈의 상세 통계 화면으로 이동한다. 전체 현황을 먼저 보고 필요한 부분만 자세히 확인하는 구조다.

```text
통합 상태 창
 ├ 현재 / 7일 전 / 1개월 전의 핵심 상태 비교
 ├ 식사 요약 → 식사 상세 통계 → 관련 기록
 ├ 산책 요약 → 산책 상세 통계 → 관련 기록
 ├ 체중 요약 → 체중 상세 통계 → 관련 기록
 └ 그 밖의 모듈 요약 → 해당 모듈 상세 통계
```

### 자기 과거와의 비교 + 같은 분류의 기준과 비교

비교는 두 방향으로 생각한다.

1. **시간 비교:** 현재와 7일 전·1개월 전 등 자기 반려동물의 과거 상태를 비교한다.
2. **기준 비교:** 해당 반려동물의 종과 기본 체격 분류에 맞는 평균·참고 범위와 현재 상태를 비교한다.

세부 품종별 기준을 전부 만드는 대신 우선 소형·중형·대형 정도의 기본 분류를 사용한다. 예를 들어 리트리버를 대형견으로 등록했다면, 해당 반려동물의 체중 등을 대형견 분류에 해당하는 평균·참고 기준과 비교해 현재 위치를 확인하는 구상이다. 다른 동물에게는 그 종에 맞는 분류와 기준을 사용한다.

사용자가 든 예시는 체중이 기준보다 낮으면 저체중처럼 상태를 알아볼 수 있게 하자는 것이다. 다만 `평균보다 낮음`과 `저체중` 판정은 구분하고, 실제로 어떤 비교 대상과 기준으로 상태를 표시할지는 이후 구체화한다. 평균보다 낮다는 이유만으로 저체중으로 확정하는 규칙을 지금 정한 것은 아니다.

통합 화면에는 기준 대비 위치를 짧게 표시하고, 자세한 비교 수치와 기준의 출처·적용 대상은 모듈별 상세 통계에서 확인하는 방향이다. 참고 기준이 없거나 기록이 부족하면 그 상태를 표시한다.

기획 단계에서는 현재·7일 전·1개월 전의 집계 방식을 검토 항목으로 두었다. 1차 구현에서는 활동량은 각 기준일까지 최근 7일, 체중은 기준일까지 마지막 측정값, 재고는 기준일 말 잔량으로 구분했다. 세부 기준은 [구현과 실행](07_구현과실행.md)에 정리했다.

## 8. 초기 설계 검토 사항

아래 항목은 초기 기획에서 세부 설계가 필요했던 부분이다. 사용자와 정한 핵심 요구사항을 바탕으로 1차 구현에서 적용한 선택과 남은 한계는 [구현과 실행](07_구현과실행.md)에 정리했다.

| 항목 | 설계 검토 내용 |
| --- | --- |
| 반려동물 등록 정보 | 필수·선택 항목과 모르는 정보의 처리 |
| 모듈 기본 배치 | 종별 초기 구성과 배치 방식 |
| 통합 상태 비교 | 시점·집계 기간, 모듈별 핵심 지표와 표시 방식 |
| 평균·참고 기준 | 출처, 적용 조건과 상태 판정 기준 |
| 게스트 수정 범위 | 본인 기록 수정·취소 등 세부 권한 |
| 초대 링크 관리 | 유효기간, 사용·인원 제한, 폐기·재발급 방식 |
| 루틴과 알림 | 반복 일정, 담당자, 상태 표시와 알림 방식 |

1차 구현에서 초대 관리는 방장 권한으로 두었으며, 투약·병원·지출은 기본적으로 방장·관리자에게만 공유하고 방장이 공개 범위를 선택하도록 했다. 기술 구성은 Django와 SQLite이며, 서비스 표시명은 임시로 ‘반려동물 돌봄’을 사용한다.

## 9. Unslop 활용과 출처 기록

1차 전체 구현 후 UI를 정돈하는 과정에 [Unslop](https://github.com/heydamir/unslop)을 활용했다. 적용 내용과 사용한 커밋, 제작자·라이선스는 [사용 도구 및 출처](../../THIRD_PARTY_NOTICES.md)와 [구현 과정 초안](../../blog/drafts/02_사이트구현.md)에 기록했다.

Unslop은 기존 화면을 검토하고 간격, 색상, 아이콘, 문구, 글자와 배치를 다듬는 스킬이다. 모듈별 화면의 일관성과 통합 상태 창의 가독성을 개선하는 용도로 사용한다. 서비스 기능과 사용자가 정한 구조를 유지하고, 개별 디자인 규칙은 우리 서비스의 사용성에 맞게 적용한다.

### 활용 기록 원칙

- GitHub의 사용 도구·출처 안내와 해당 개발 단계의 블로그에 Unslop을 사용했다는 사실과 저장소 링크를 적는다.
- 어떤 화면의 어떤 문제 때문에 사용했는지, 무엇이 바뀌었는지, 제안 중 무엇을 채택하거나 수정했는지 실제 결과를 기록한다.
- 적용 전후 화면과 확인 결과가 있으면 함께 남긴다. 사용하지 않은 기능이나 수행하지 않은 검사를 사용·완료한 것처럼 쓰지 않는다.
- 실제 적용 시 사용한 버전 또는 커밋을 확인해 기록한다.
